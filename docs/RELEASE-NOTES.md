### A new name: Relay

- **Relay:** Gym Logger is now called Relay, with a new blue R icon on sign-in, in the browser tab, in notifications, in the installed app and on the Home Screen guide. Accounts, training history, settings and sign-in are unchanged.
- **Home Screen:** start at **https://relayfitness.app**. The illustrated installation guide links to the new address and shows it in Safari’s toolbar and share sheet. On iPhone, add the app to your Home Screen again to show the new name and icon.
- **Imports:** choose **Relay** for native workout and bodyweight CSVs, including files exported from Gym Logger. The CSV template downloads as `relay-workout-template.csv`.
- **Repository:** the GitHub repository is now [ejbolts/Relay](https://github.com/ejbolts/Relay); links to the old name redirect.

### Training in one place

- **Training:** one bottom tab combines **Sessions**, **Exercises** and **Cardio**. Sessions keeps the full calendar, date details, machine filtering, notes, photos and existing workout actions. Your open session and selected exercise remain when you visit another tab. Sessions initially shows the latest workout week and the two preceding calendar weeks, respecting your week-start preference. Show more reveals older sessions; calendar and exercise links can still open older workouts directly. [#107](https://github.com/ejbolts/Gym-logger/pull/107)
- **Exercises:** option A replaces the library/preview split with a full exercise list and a focused detail view. Search by exercise or equipment, filter by muscle group, and cycle Recent first, A-Z and Most improved sorting. Rows show recent estimated 1RM, an eight-week trend and change; untrained lifts remain available. Tap a lift for per-session charts, personal bests and session history. Session rows open a set sheet with weight, reps, RPE and an Open workout action. Back to Exercises retains the query, filter, sort, scroll, metric and range. The list loads its account-owned trends in one request, excluding future sessions, warmups and unfinished sets.

- **Cardio weekly trends:** one card replaces the separate cardio-time, METs and previous-weeks cards. Switch between time, distance, MET-minutes and calories burnt; tap any of the last eight weeks for its totals, previous-week comparison and duration-weighted averages. **All stats** opens the familiar metrics and longer date ranges in a compact grid. The displayed week uses the full calendar range while totals exclude future sessions. History groups expandable session rows by your preferred week start, retaining filters, pagination, source-workout links and editing actions. **Log session** and **Import screenshot** are available above the chart; screenshot OCR still fills the form for review before saving.

## Publishing the next announcement

1. Edit `frontend/release.json`. Choose the version manually following [the agent release policy](../AGENTS.md#release-versions-and-announcements). Before merging a batch, [evaluate the currently open GitHub PRs](../AGENTS.md#reviewing-and-merging-a-pr-batch), select the included PRs and reconcile their release metadata. A coordinated batch of multiple PRs for an application release gets **one minor bump** (`0.3.0` to `0.4.0`), even if its changes are mostly patches. Every PR in that batch shares the version and contributes to one announcement; do not accumulate its individual version proposals. Reuse an already pending minor release for that batch, consolidate unpublished patch notes into it, and retain the version for follow-up fixes before deployment. For an independently released single PR, default to a patch (`0.3.0` to `0.3.1`); a substantial new capability can justify a minor bump. Documentation/test/tooling-only batches with no application behavior change need no app bump. Compare deployed and pending versions, never reuse a deployed number, and preserve deployed release history. Before replacing a deployed release's notes, move its existing `release.json` object to the top of `frontend/release-history.json` so the app keeps showing it under **Earlier versions**; leave unpublished pending versions out of the history. Update `title`, `summary`, `changes` and `url`. `url` must be an HTTPS GitHub link to your release, changelog or pull request. The build validates the metadata but does not increment versions automatically.
2. Add the detailed notes here (keep previous versions), or publish a GitHub release and link to it instead. If this repository is private, readers need GitHub access to open that link; the short notes remain visible inside the app.
   Put the release heading, date and title first, then the feature screenshots and animated GIFs with descriptive alt text and captions, followed by the change bullets. Keep this media-first order in the app announcement and published GitHub Release notes too.
   For a visible feature or UI improvement, include a screenshot of the verified revision using isolated sample data. When a selected feature recording is MP4 or WebM, convert it to a short, looping GIF that preserves the real interaction and readable final result; decode and visually review the converted file for quality and private information. Embed the GIF as an image, not a video link. Keep the original recording locally and preserve existing published media URLs. Commit release screenshots/GIFs under `docs/screenshots/releases/` with versioned filenames and use relative image paths here. Before/after images are useful when they clarify the change. Explain omitted screenshots in the notes or pull request when capture is unavailable or the change has no visible result.
   The optional `image` object in `frontend/release.json` uses `url` and `alt` to display a selected screenshot or GIF in the app's pop-up. Use a direct HTTPS `raw.githubusercontent.com` image URL pinned to the media's commit, not a GitHub page URL or temporary browser-artifact path. Check anonymous access before publishing; private-repository images may not be accessible to app users. If the image is unavailable, the app still shows the text and dismissal controls.
3. Test the feature and announcement locally. Dismissal is remembered for each version; **View changes** always reopens the dialog without clearing browser data.
4. Commit and push the code and metadata for review. The announcement is included in the frontend build; editing the source metadata alone does not update an existing build.
5. Before an authorized deployment, follow [release preparation](../AGENTS.md#preparing-release-notes-before-deployment). Correct the existing open feature/coordinating PR, or create a focused preparation PR if the code is already on `main` and the notes/media still need work. Include the reviewed GIFs and media-first notes, retain the selected release version, and obtain the required approval and merge authorization before deployment. After merging, select and verify the exact `main` revision containing the prepared release content. For published GitHub Release notes, replace relative image/GIF paths with raw URLs pinned to the deployed tag's commit and verify their rendered order.

Vite emits `release.json` into `frontend/dist` with the app and serves it directly during development. The browser checks that deployed file using `cache: no-store`; the service worker does not precache it. The announcement therefore follows the current frontend build. Changing source notes without rebuilding the frontend leaves its announcement unchanged.

If users miss several releases, they see the latest notes and can expand earlier versions in the same pop-up. The build rejects a history entry that is invalid, out of order, duplicated or not older than the current version. Network failures leave the app usable and are retried when it returns to the foreground or reconnects. Dismissal survives sign-out; deleting browser storage shows the notes again. Browsers that block storage remember dismissal for the current page session only.
